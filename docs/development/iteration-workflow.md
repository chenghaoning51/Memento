# 迭代与交付流程

本文规定如何把[开发计划](plan.md)执行成可验收的增量。流程从后续开发开始采用；测试工具、CI 和发布自动化仍待接入，不代表当前仓库已有这些能力。

## 角色与容量

- 暂按 1 名开发者负责前端、Rust、测试与文档；产品范围和阶段交付由项目负责人评审。人员增加后可分工，但保留一名阶段交付负责人。
- 两周一个迭代，以约 8 个有效开发日安排任务；阶段估算中的额外风险缓冲不作为必做功能填满。
- 每轮只有一个主目标，例如“日记保存并重开”，而非同时开始所有导航页面。
- 同一开发者最多一个实现任务处于进行中，另有一个任务可以等待评审；依赖阻塞时先记录阻塞原因，再选择不依赖它的工作。

## 一轮迭代如何推进

| 时间点 | 动作 | 产出 |
| --- | --- | --- |
| 开始前/第 1 天 | 核对阶段门槛、上轮缺陷和可用容量，选取本轮任务 | 主目标、任务列表、验收编号、已知依赖与不包含的范围 |
| 每个开发日 | 检查昨天已完成的证据、今天要验证的行为和阻塞 | 简短执行记录；新增风险或估算变化及时写回 |
| 中段，约第 5 个工作日 | 演示真实桌面流程，检查上下层是否已经连通 | 可复现的中间结果；必要时减少本轮范围 |
| 最后 1–2 个工作日 | 停止扩大范围，执行回归、修复和文档核对 | 验收结果、缺陷、剩余风险和阶段判断 |
| 结束时 | 对比预计与实际，演示并评审，安排下一轮 | 完成/未完成清单、下一轮候选任务与更新后的估算 |

以上时间点是两周工作节奏，不假设每天都能完成一个任务。单个阶段可以跨多轮迭代；一轮结束也可以停在阶段内部，不能将未通过门槛的阶段标为完成。

## 开始任务的条件

任务进入“进行中”之前，应具备：

- 清晰的用户行为和边界，能在一到两个工作日内验证；超过两天先拆分。
- 对应的产品文档、架构依据和验收编号，至少有一条具体成功或失败示例。
- 前置数据、接口与依赖已就绪；涉及新依赖或跨模块约定时，相关 ADR 已接受。
- 已说明对旧数据、迁移、正文、附件和备份的影响。
- 明确验证方式，区分现有命令、待建立的测试和必须在桌面执行的场景。

技术选型验证可以单独成为任务，但必须限制时间，并产出选择依据、可运行样例与结论，不能把“调研完成”替代功能验收。

## 任务如何记录

阶段和任务编号来自开发计划。实际执行时在 `docs/development/iterations.md` 末尾追加一轮；不预建空白迭代，也不把计划勾选为完成。

每份迭代记录至少包含以下内容：

```markdown
## 迭代 NNN

- 日期：开始日至结束日
- 所属阶段：M1
- 负责人：姓名
- 主目标：用户能够完成的一个具体流程
- 可用容量：有效开发日

| 任务 | 范围与依赖 | 负责人 | 估算/实际 | 状态 | 验收编号与证据 |
| --- | --- | --- | --- | --- | --- |
| M1-01 | 本轮实现范围 | 姓名 | 2 日 / 待记录 | 待开始 | A01，待验收 |

### 本轮验收

- 环境、提交或工作区版本、命令与结果。
- 桌面场景的操作、预期、实际和证据位置。
- 缺陷、风险、未完成项与下轮安排。
```

状态使用“待开始 → 进行中 → 待验收 → 完成”；阻塞时标“阻塞”并写出原因、影响和下一步。只有证据通过才进入完成；延期任务保留原编号和已经发现的问题。

## 完成任务的条件

- 产品行为符合场景，真实数据链路可操作；占位页面、模拟保存和只显示成功提示不满足完成条件。
- 加载、空、错误、取消和成功状态按场景处理；涉及持久化时覆盖重开、失败与重试。
- 没有绕过 UI → 应用服务 → Tauri → 本地存储的边界，相关 ADR 和数据文档已更新。
- 执行现有构建检查，针对高风险行为增加有价值的测试；测试工具在引入后才作为强制命令。
- 相关验收条目有结果和证据，阻断缺陷已修复；已有核心场景继续通过。
- 用户可见功能更新 `docs/changelog.md`；产品、架构、命令和流程变化更新相应文档。命令或流程变化同步根 README。
- 代码和文档纳入同一评审变更，更新迭代记录；达到阶段门槛时再更新路线图状态。

文档修改、低风险样式或文字调整以构建、链接/格式与人工检查为主，不为了形式新增镜像实现的测试。

## 缺陷分级与处理顺序

缺陷使用 S 级别，避免与产品 P0/P1/P2 优先级混淆。

| 级别 | 例子 | 处理规则 |
| --- | --- | --- |
| S0 数据事故 | 已保存内容丢失、图片被误清理、恢复覆盖后无法回退 | 停止相关功能开发与发布，保留复现数据，修复并验证完整性后继续 |
| S1 主流程阻断 | 无法保存/重开、备份无法恢复、已到期信件无法阅读 | 优先于新功能处理；阶段和发布均不可带入 |
| S2 功能明显偏差 | 特定组合筛选漏项、键盘操作不可达、状态提示错误 | 涉及本阶段验收的先修复；发布前所有 P0 条目必须通过 |
| S3 体验细节 | 非阻断的间距、排版或文案问题 | 按容量安排；遗留项记录影响与后续处理 |

每个缺陷记录版本、环境、最小复现、预期、实际、影响数据与复测结果。复现数据使用合成内容，不把真实私人日记提交到仓库。

## 阶段和发布评审

- 阶段评审核对开发计划中该阶段的退出门槛、相关验收条目和此前已通过的核心回归。
- 缺少证据或验收失败时保留“进行中”，明确待修任务；不能以进度百分比代替门槛。
- M1 后重算后续工期；之后每阶段根据实际速度、缺陷和决策变化更新计划。
- 发布须额外满足[发布验收门槛](acceptance.md#发布验收门槛)，记录实际验证过的安装包与环境。
- 每次新增命令或自动化能力，同步开发环境文档和根 README；不要在计划中把尚不存在的脚本写成已可执行。

## 代码约定

## 命名

- React 组件使用 PascalCase。
- Hooks 使用 `use` 前缀。
- 产品概念在代码中保持固定名称：`entry`、`attachment`、`letter`、`tag`。
- 服务器或 Rust 层的时间字段明确使用 `_utc` 后缀；用户日历字段使用 `entry_date`。

## 目录

- `app/` 只处理应用壳、导航和全局布局。
- `features/` 按产品能力分组，不按组件类型拆散业务逻辑。
- `components/` 只放跨功能复用组件。
- `lib/` 放无 UI 副作用的基础函数和客户端封装。
- `src-tauri/` 负责本地系统能力和数据边界。

## 状态和保存

- 编辑器的临时输入状态留在前端，持久化由应用服务统一处理。
- 自动保存必须可取消、可重试，并且在失败时保留用户当前输入。
- UI 的“已保存”状态只能在持久化成功后显示。
- 不在组件中散落文件路径拼接和数据库 SQL。

## UI 质量

- 所有页面需要有加载、空、错误和成功后的状态。
- 装饰不能遮挡正文，也不能改变编辑器尺寸。
- 按钮和输入控件保留键盘焦点样式。
- 颜色和字体统一来自全局设计令牌。
- 文案不使用连续打卡、惩罚或公开社交暗示。

## 提交前检查

```bash
pnpm build
cargo check --manifest-path src-tauri/Cargo.toml
cargo test --manifest-path src-tauri/Cargo.toml
git diff --check
```

新增文件还需检查内容、链接和格式；未跟踪文件不在 `git diff --check` 的检查范围内。前端暂无测试脚本，不假设已有。

Rust 测试放在 `src-tauri/src/tests.rs`，用真实临时目录建库，覆盖迁移、持久化、附件、检索、信件状态、导出与备份恢复；不为纯转发命令或界面文案写镜像测试。桌面行为（对话框、窗口、时区）靠迭代记录里的手工验收，不写模拟脚本。

## 任务与验收

- 阶段、优先级和前置任务见[开发计划](plan.md)。
- 两周迭代、开工条件、完成定义和缺陷处理见[迭代流程](iteration-workflow.md)。
- 任务引用[验收清单](acceptance.md)中的编号，在迭代记录保留执行环境、步骤、结果和证据。
- 保存、迁移、附件、备份和恢复必须验证失败路径；纯外观或文档调整按风险进行检查。
- 只有真实数据流程通过验收，才能更新任务和阶段为完成；产品功能变化同步变更记录。
