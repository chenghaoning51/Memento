### 桌面场景

| 编号 | 操作 | 预期 | 实际 | 结果 |
| --- | --- | --- | --- | --- |
| A13 | 创建未来信件，在开启时刻前、等于时刻、时刻后分别进入；关闭应用到期后重开 | 未到期显示锁定；到期按既定规则可阅读；重启不重置状态；原始时区可以解释开启意图 | 见下方明细 | 通过 |
| A14 | 到期打开原信并追加回应，关闭重开；对 F4 时区样例重复 | 原信和回应分别完整，打开状态一致；切换时区不漂移既定开启时刻；仅限制应用内体验，不宣传为加密封存 | 见下方明细 | 通过 |

A13 明细：

- 开启日期设为次日：列表显示“还有 1 天开启”，锁定期内点开只进入编辑态，正文不出现；数据库中 `unlock_at_utc` 为所选日期 00:00 按 `Asia/Shanghai` 换算的结果（`2026-10-18T16:00:00.000Z`），`unlock_timezone` 同时落库。
- 把开启时刻改到当前时刻之前并强制结束进程，重开应用进入“未来信箱”：该信在列表里变为“可以打开”，点开后显示原信正文与“原信 / 2026年10月18日 12:45 开启”，说明状态按当前 UTC 重算而不是依赖进程内的定时器。
- 打开后列表变为“读过，可以补回应”，数据库中 `status = opened` 且 `opened_at_utc` 有值；再重启一次仍是 `opened`，打开时间不变。
- 未到期的信点开后是编辑态：标题、正文、开启日期都可改；到期后再点开则直接进入阅读态，编辑入口不再出现。

A14 明细：

- 到期后写“到期之后写下的第一句回应。”并保存，切到时间线再回到未来信箱，重开该信：回应仍在输入框，原信正文不变，列表显示“读过，可以补回应”。
- 把系统时区切到 `America/New_York` 打开同一封信：列表日期仍是“2026年10月17日”，顶栏“2026年10月17日 00:00 开启”，按写信时区解释，没有漂成前一天。
- 在纽约时区新建 2026-12-25 的信：`unlock_at_utc = 2026-12-24T16:00:00.000Z`、`unlock_timezone = Asia/Shanghai`；再在纽约时区只改正文不改日期，两个字段都不变。
- 在纽约时区把开启日期改成 2026-10-20（夏令时，UTC−4）：`2026-10-20T04:00:00Z`；改成 2026-12-25（标准时，UTC−5）：`2026-12-25T05:00:00Z`，时区标签同时变为 `America/New_York`，预览与保存值一致。
- 回到上海时区打开纽约时区写的信：列表日期“2026年11月1日”、编辑态顶栏“2026年11月1日 00:00 开启”、日期框回填 `2026-11-01`，既定开启时刻没有被重新换算。
- 页面文案只写“在应用里保持关闭”，并明确“这不是加密，只是给自己的一个约定”，没有出现“已加密”“安全封存”一类说法。

### 缺陷

| 级别 | 现象 | 处理 |
| --- | --- | --- |
| S2 | 换时区后阅读态顶栏用本机时区格式化开启时刻，与列表里按写信时区显示的日期对不上 | 已修复：新增 `formatMomentInZone`，阅读态与编辑态顶栏统一按 `unlock_timezone` 格式化 |
| S2 | 换时区后打开编辑并保存，会让已约定的开启时刻漂移 | 已修复：日期没改就沿用原来的 `unlock_at_utc` 与 `unlock_timezone`；改了日期才按当前时区重算，时刻与时区标签始终成对 |
| S2 | 距离开启只剩十几秒时，列表显示“还有 1 天开启” | 已修复：天数改为按写信时区数日历日，同一天显示“今天开启” |
| S2 | 已到期但还没打开过的信，库里状态仍是 `locked`，因此仍可被编辑 | 已修复：`update_letter` 同时判断状态列与当前时刻；前端点开编辑前先复核一次状态，到期就直接进阅读态 |
| S3 | 列表上的“还有 N 天”会随页面停留时间自己跳 | 已修复：天数按进入页面时取的“现在”计算，不在渲染中读时钟 |

另有一次开发期故障：改了前端页面后应用报 `ReferenceError`，整页白屏。原因是 vite dev server 缓存了旧模块，重启 dev server 后恢复；不是产品缺陷。

### 风险与未完成项

- 锁定只是应用内的展示限制，数据库里的正文没有加密；产品文案与代码注释都不把它描述成加密或安全封存。
- 状态只在读取时按当前 UTC 推进，`status` 列可能停在 `locked` 而内存里已推进为 `unlocked`；真正落库的只有打开与回应。若将来增加定时提醒，需要新的设计。
- 信件目前没有纳入备份与恢复（M5）；[ADR-0005](../decisions/0005-attachment-files.md) 之后新增的 `letters` 表与回应需要在 M5 的备份清单里显式覆盖。
- 回应是纯文本 textarea，没有富文本与图片；原信与回应都不支持历史版本。
- 前端仍无测试与 CI；时区与夏令时场景靠桌面手工验证与两个 Rust 用例兜住状态判定。
