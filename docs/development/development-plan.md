# MVP 开发计划

- 规划基线：2026-10-17。
- 目标：交付 Windows 上完全离线可用、内容可可靠保存并能完整恢复的 MVP。
- 状态：M0、M1 已完成，M2 进行中（M2-01、M2-02 已完成）；除“当前基线”明确列出的能力外，下文均为待实施工作。
- 范围依据：[产品愿景](../product/vision.md)、[MVP 范围](../product/mvp-scope.md)。
- 配套文档：[迭代流程](iteration-workflow.md)、[验收清单](acceptance.md)、[路线图](../roadmap.md)。

## 1. 当前基线与框架理解

M1 之后已经形成“创建 → 编辑 → 自动保存 → 关闭重开”的保存闭环；M2-01 加入格式编辑，M2-02 加入图片。仍缺标签、回收站、检索、信件、导出与备份。

| 层次 | 当前实现与证据 | 开发时需要补齐 |
| --- | --- | --- |
| 前端入口 | `src/main.tsx` 挂载 React，加载全局样式 | 保持入口轻量，不承载业务逻辑 |
| 应用壳与导航 | `src/app/App.tsx` 通过组件状态切页；“今天”与“设置”是真实页面，其余走 `features/placeholder/SectionPage.tsx` | 继续替换占位页，处理编辑中切页和日期定位 |
| 功能页面 | `features/today/TodayPage.tsx` 接真实数据；`features/settings/SettingsPage.tsx` 显示数据位置 | 时间浏览、搜索、未来信件、标签与回收站 |
| 应用服务与类型 | `src/lib/entryApi.ts` 封装命令，`src/lib/entryContent.ts` 维护正文 JSON，`src/lib/localDate.ts` 处理本地日历日期，`src/types/entry.ts` 定义共享类型 | 随新功能扩展服务层，保持 UI 不碰 SQL 和文件路径 |
| 编辑与保存 | `src/features/today/useAutosave.ts`：800 ms 空闲保存、最多 5 秒强制保存、串行写入、失败重试、切页与关闭前 flush；`EntryEditor.tsx` 承载 Tiptap 工具栏与图片导入 | 标签与回收站交互、持续回归撤销与粘贴 |
| 视觉基础 | `src/styles.css` 包含颜色令牌、排版与响应式布局 | 随真实交互补充组件和键盘操作，不以重做外观阻塞主流程 |
| 前端依赖 | React 19、TypeScript 6、Vite 8、Tauri API 2、Lucide、Tiptap 3.32 | 新增依赖前完成 ADR |
| 桌面入口 | `src-tauri/src/lib.rs` 在 setup 中打开 Library、注册七个命令与 `attachment` 自定义协议 | 导入导出与备份命令 |
| Rust 模块 | `db/migrations.rs` 顺序迁移、`library.rs` 连接与 WAL、`entries/repository.rs` 与 `attachments/repository.rs` 仓储、`attachments/mod.rs` 图片识别与缩略图、`commands.rs` 七个命令、`error.rs` 统一错误 | 标签、回收站、信件与备份 |
| Rust 依赖 | Tauri 2、Serde、Serde JSON、rusqlite（bundled）、time、uuid、sha2、image 0.25（只开 png/jpeg） | 按阶段选择，引入前写 ADR |
| 权限与打包 | 窗口配置、应用标识和图标；capability 含 `core:default` 与 `core:window:allow-destroy`；CSP 当前为 `null` | 验证业务命令权限、内容加载边界与 Windows 安装升级 |
| 质量基础 | `pnpm build`、`cargo check` 与 `cargo test`（5 个用例）通过；桌面验收见[迭代 001](iterations/iteration-001.md)与[迭代 002](iterations/iteration-002.md) | 前端测试、固定验收数据与 CI |

`src/components/` 仍为空缺，等出现跨功能复用组件时再建立，避免空目录先行。仓库已有首个提交作为版本基线，Rust 侧有 `cargo test`，但前端仍无测试命令、也没有 CI 工作流；构建通过不代表持久化或桌面业务已经验证。

后续沿用既有[系统架构](../architecture/overview.md)：

```text
React 页面与编辑状态
  → 应用服务
    → Tauri 命令
      → Rust 数据与文件操作
        → SQLite + 独立附件目录
```

UI 不直接操作数据库或文件系统。正文结构、搜索文本和附件分别管理；UTC 时间戳与本地日历日期分别保存。本文不新增数据契约，具体选型和格式在实施前通过 ADR 确定。

## 2. 优先级与取舍

产品优先级沿用 MVP 文档；阶段顺序表示依赖，不改变功能的重要性。

| 优先级 | 工作范围 | 安排理由 |
| --- | --- | --- |
| P0：MVP 必须交付 | 本地存储与迁移、日记编辑与自动保存、图片与标签、回收站、时间地图与时间线、搜索、未来信件、Markdown 导出、完整备份恢复、Windows 发布验证 | 缺少任一部分都无法完成既定 MVP 闭环 |
| P1：MVP 稳定后评估 | 收藏卡片与主题册、月份切片、全局快速捕捉、最近位置与草稿恢复细节、应用锁与凭据保护 | 复用已验证的数据能力，避免扩大第一版交付面 |
| P2：暂不实施 | 自由画布与贴纸、云同步与移动端、多人协作、AI 整理、公开分享和社交 | 涉及新的产品边界或基础设施，另行规划 |

P0 内部按下列顺序取舍：数据不丢失与可恢复 → 一条可操作的完整流程 → 查找与回看 → 丰富展示和交互细节。不能因为备份位于后续阶段，就将其降为可选功能。

出现时间压力时，先减少并行任务、收敛视觉细节和重新估算；不能删除自动保存失败处理、图片完整性、回收站或备份恢复，也不能把占位入口记为完成。P0 的范围变更必须先修订产品文档和验收条目。

## 3. 阶段、依赖与工期假设

按 1 名能同时负责前端和 Rust 的开发者估算，每周约 4 个有效开发日；每阶段工作量包含设计、实现、测试、文档和修复。没有预设启动日期，以下不是日历交付承诺。

| 阶段 | 交付目标 | 前置条件 | 估算有效开发日 | 退出门槛 |
| --- | --- | --- | --- | --- |
| M0 开发准备与关键决策 | 细化 P0 边界、建立验收数据、确定第一条链路所需选型 | 当前骨架 | 2–3 | 范围、ADR、最小任务和验证方法可执行 |
| M1 第一条可靠保存链路 | 创建一篇文本日记，保存后关闭重开可继续编辑 | M0 | 5–8 | 数据库迁移、真实持久化、保存状态与失败处理通过 |
| M2 日记编辑闭环 | 格式编辑、图片、标签、删除和恢复 | M1 | 8–12 | 带图片的中文长文可稳定编辑与恢复 |
| M3 时间回看与检索 | 时间线、月历、日期详情、搜索与筛选 | M2 | 6–9 | 同一批真实记录可从日期、标签与关键词找回 |
| M4 未来信箱 | 创建、锁定、到期阅读和回应 | M3 | 4–6 | 开启时间与跨重启状态正确，信件和回应可靠保存 |
| M5 导出、备份与恢复 | Markdown 与图片导出、完整备份、校验和恢复 | M4；格式设计从 M0/M1 开始 | 5–8 | 全新空间恢复等价；失败不破坏当前空间 |
| M6 发布加固与 Windows 验收 | 回归、故障验证、性能检查、安装升级和发布说明 | M1–M5 均通过 | 5–7 | P0 清单通过，无阻断缺陷，发布证据齐全 |

总计约 35–53 个有效开发日；预留约 20% 的集成与未知问题缓冲后，按 42–64 日、约 11–16 周规划容量。M1 完成后用实际耗时、技术验证和缺陷数量重新估算；增加人员不直接按人数等比例缩短关键链路。

```mermaid
flowchart LR
  M0["M0 范围与决策"] --> M1["M1 可靠保存"]
  M1 --> M2["M2 编辑与附件"]
  M2 --> M3["M3 回看与检索"]
  M3 --> M4["M4 未来信箱"]
  M4 --> M5["M5 导出与恢复"]
  M5 --> M6["M6 Windows 发布"]
```

阶段可以跨迭代，但退出门槛不能跳过。M1–M5 使用可丢弃的验收数据做内部演示；完整备份、恢复与 M6 验收通过后才作为承载重要私人内容的 MVP 发布。

## 4. 阶段任务与验收

M0、M1 任务已完成，M2-01 已完成，M2-02 起与 M3–M6 任务初始状态为“待开始”。建议每次只把当前阶段接下来 1–2 周的任务细拆为半天至两天的工作项，不提前把后续阶段写成大量无法验证的小任务。

### M0：开发准备与关键决策

| 编号 | 任务与产出 | 完成依据 |
| --- | --- | --- |
| M0-01 ✅ | 逐项细化 MVP 场景；明确撤销与恢复、回收站、信件开启日期和备份恢复的产品语义 | 产品文档能回答成功、失败、取消与重启后的行为；对应验收条目没有歧义 |
| M0-02 ✅ | 对 SQLite 接入方式、编辑器候选与正文格式做最小验证 | 决定后新增 Accepted ADR；记录维护成本、迁移方式、中文输入和 Rust 边界验证结果（Tiptap 已在 M2-01 按 [ADR-0004](decisions/0004-tiptap-editor-and-content-v2.md) 接入） |
| M0-03 ✅ | 建立最小质量流程与固定验收数据；处理当前尚无版本基线的问题 | 检查命令可复现；测试依赖如需引入先写 ADR；首个持久化任务具备测试入口；版本基线纳入正常评审提交 |

备份清单需要包含哪些业务数据、附件相对路径如何演进，须在 M0/M1 的数据设计中说明；归档容器与恢复实现的具体选型可以留到 M5，不能等到 M5 才发现数据无法完整导出。

退出条件：能说明“写入什么、存到哪里、如何确认成功、如何失败恢复”，并可从 M1-01 开始实现。M0 本身不意味着数据库和编辑器已经完成。

### M1：第一条可靠保存链路

| 编号 | 任务与产出 | 完成依据 |
| --- | --- | --- |
| M1-01 ✅ | Rust 数据目录初始化、SQLite 初始迁移与仓储；确定应用数据目录并在设置中可查看 | 首次启动可建库，再次启动不重复迁移；失败可理解，不静默新建空库覆盖旧库 |
| M1-02 ✅ | 最小日记命令、应用服务和真实创建/加载页面 | 可创建不同 ID 的日记，日期按本地日历保存；接口契约依 ADR 和架构文档维护 |
| M1-03 ✅ | 基础文本编辑、自动保存及切页/关闭处理 | 已保存只在持久化成功后出现；快速连续输入不会被较早请求覆盖；失败保留输入并可重试 |
| M1-04 ✅ | 保存、重启、迁移和失败场景验证 | [A01–A05、A15](acceptance.md#功能与可靠性验收矩阵) 通过，留下复现步骤与证据 |

演示脚本：首次启动 → 新建中文日记 → 连续修改 → 确认已保存 → 切页返回 → 正常关闭 → 重开继续编辑 → 模拟一次保存失败并恢复。

退出条件：数据不依赖浏览器内存或演示数据；首次迁移、真实磁盘保存、重启恢复和异常状态都可验证。M1 仅为内部里程碑，尚不等于完整编辑器。

### M2：日记编辑闭环

| 编号 | 任务与产出 | 完成依据 |
| --- | --- | --- |
| M2-01 ✅ | 标题、引用、分隔线、链接、撤销等编辑能力；同步维护结构化正文和搜索文本 | 中文输入法、粘贴、撤销和重开后内容正常，正文格式有版本策略 |
| M2-02 ✅ | 图片导入、附件元数据、相对路径、首图和需要的缩略图 | 多图可显示；原文件删除或移动后仍可阅读；失败没有损坏正文引用 |
| M2-03 | 标签编辑、日记软删除、回收站列表与恢复 | 删除记录不再出现在正常浏览中；恢复后正文、图片和标签关系完整 |
| M2-04 | 编辑器与附件故障回归 | [A06–A09](acceptance.md#功能与可靠性验收矩阵) 通过，M1 用例继续通过 |

附件和数据库写入顺序、失败清理、备份期间的一致性必须一并设计，结论见 [ADR-0005](../decisions/0005-attachment-files.md)：先写文件后插行，失败回滚文件，正文只记附件 ID。回收站中的附件不能当作孤立文件清除；永久删除和自动清理的产品规则未确定前不自行加入。

退出条件：完全离线写入中文长文和多张图片，能保存、重开、删除、恢复；错误情况下保留可恢复的内容。

### M3：时间回看与检索

| 编号 | 任务与产出 | 完成依据 |
| --- | --- | --- |

退出条件：能从关键词、标签和日期找到目标内容，并进入同一条真实日记；不引入未经验证的中文全文检索依赖。

### M4：未来信箱

| 编号 | 任务与产出 | 完成依据 |

### M5：导出、备份与恢复

| 编号 | 任务与产出 | 完成依据 |
| --- | --- | --- |
| M5-01 | Markdown 与图片导出 | 路径、中文文件名和重名处理明确；格式降级规则已写入产品文档；图片引用在应用外可用 |
| M5-02 | 完整备份、版本化 manifest、文件清单与校验 | 快照与附件一致，包含回收站、标签、信件、回应和需要恢复的设置；格式先写 ADR |

退出条件：导出可独立阅读；备份实际恢复后，正文、图片、标签、回收站、信件和回应可核对；失败时当前空间仍可打开。

| 发布目标系统与分发方式 | M6 前 | 开发/发布文档；指定实测 Windows 版本和架构，不提前宣称多平台支持 |

本次仅把既有范围转化为执行计划，没有引入依赖、改变表结构或接受新的跨模块协议，因此不新增 Accepted ADR。此表中的决策完成后才更新架构文档和相应实现。

## 6. 开发节奏与计划维护

- 使用两周一个迭代；每轮按约 8 个有效开发日规划，阶段门槛与迭代边界分别管理。
- 每轮只承诺一个可演示的主目标；同一时间只推进一条尚未验收的业务链路，优先处理数据可靠性缺陷。
- 启动时从本计划选任务，补充范围、依赖和验收编号；中段演示真实桌面流程；结束时回归、核对证据并重新估算。
- 每个功能任务完成产品/架构文档、实现、必要验证和变更记录；阶段状态在路线图维护，任务执行记录放入迭代记录。
- M1 后和每个阶段结束时，用实际耗时与剩余风险调整容量。技术问题超出一天仍未定位时，停止扩大功能面，先做有结论的技术验证。

具体开工条件、完成定义、缺陷分级和迭代记录格式见[迭代流程](iteration-workflow.md)；可执行场景、测试数据和发布门槛见[验收清单](acceptance.md)。

## 7. 主要风险与应对

| 风险 | 最早验证点 | 处理方式 |
| --- | --- | --- |
| 保存请求乱序、关闭窗口或写入失败导致内容丢失 | M1 | 验证连续输入、旧响应、失败重试、关闭与重启；持久化成功后才显示已保存 |
| 中文输入法、编辑器 JSON 演进和粘贴损坏正文 | M0/M2 | 选型时做中文最小样例；按版本处理正文；对关键格式往返保存验证 |
| SQLite、正文引用和附件文件不一致 | M1/M2 | 提前设计写入顺序、失败恢复和清理；备份与回收站使用同一完整性要求 |
| 日期和时区造成日记归属或开启日期偏移 | M1/M4 | 独立验证日历日期与 UTC；覆盖跨午夜、切换时区和夏令时场景 |
| 备份生成成功但无法恢复 | M5 | 用全新空间实际恢复并核对内容；破损输入与失败中断均保留当前空间 |
| 中文子串搜索或大图使桌面卡顿 | M3/M6 | 用固定规模记录和图片测量；先限制一次载入量，是否换索引由证据和 ADR 决定 |
| 估算缺少历史速度、Windows 安装验证滞后 | M1/M6 | M1 后重估；尽早验证开发机打包可行性，发布时再做干净环境与升级验收 |
