# 开发约定

## 命名

- React 组件使用 PascalCase。
- Hooks 使用 `use` 前缀。
- 产品概念在代码中保持固定名称：`entry`、`attachment`、`letter`、`tag`。
- 服务器或 Rust 层的时间字段明确使用 `_utc` 后缀；用户日历字段使用 `entry_date`。

## 目录

- `app/` 只处理应用壳、导航和全局布局。
- `features/` 按产品能力分组，不按组件类型拆散业务逻辑。
- `components/` 只放跨功能复用组件。
- `lib/` 放无 UI 副作用的基础函数和客户端封装。
- `src-tauri/` 负责本地系统能力和数据边界。

## 状态和保存

- 编辑器的临时输入状态留在前端，持久化由应用服务统一处理。
- 自动保存必须可取消、可重试，并且在失败时保留用户当前输入。
- UI 的“已保存”状态只能在持久化成功后显示。
- 不在组件中散落文件路径拼接和数据库 SQL。

## UI 质量

- 所有页面需要有加载、空、错误和成功后的状态。
- 装饰不能遮挡正文，也不能改变编辑器尺寸。
- 按钮和输入控件保留键盘焦点样式。
- 颜色和字体统一来自全局设计令牌。
- 文案不使用连续打卡、惩罚或公开社交暗示。

## 提交前检查

```bash
pnpm build
cargo check --manifest-path src-tauri/Cargo.toml
cargo test --manifest-path src-tauri/Cargo.toml
git diff --check
```

新增文件还需检查内容、链接和格式；未跟踪文件不在 `git diff --check` 的检查范围内。前端暂无测试脚本，不假设已有。

Rust 测试放在 `src-tauri/src/tests.rs`，用真实临时目录建库，覆盖迁移、持久化、附件、检索、信件状态、导出与备份恢复；不为纯转发命令或界面文案写镜像测试。桌面行为（对话框、窗口、时区）靠迭代记录里的手工验收，不写模拟脚本。

## 任务与验收

- 阶段、优先级和前置任务见[开发计划](development-plan.md)。
- 两周迭代、开工条件、完成定义和缺陷处理见[迭代流程](iteration-workflow.md)。
- 任务引用[验收清单](acceptance.md)中的编号，在迭代记录保留执行环境、步骤、结果和证据。
- 保存、迁移、附件、备份和恢复必须验证失败路径；纯外观或文档调整按风险进行检查。
- 只有真实数据流程通过验收，才能更新任务和阶段为完成；产品功能变化同步变更记录。
