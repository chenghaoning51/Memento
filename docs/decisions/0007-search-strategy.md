# ADR-0007：用折叠小写的搜索列做子串匹配

- 状态：Accepted
- 日期：2026-10-17

## 背景

M3-02 要让日记能按关键词、标签和日期范围组合找回。M0 的数据模型把"标题与正文的规范化子串搜索"写成了第一版策略，但没有定下三件具体的事：搜索匹配在哪个字段上做；匹配是否区分大小写与空白；索引怎么维护才和正文保存保持一致。

约束来自已有实现和产品文档：`content_text` 已经是正文的纯文本副本，但它是原样的多行文本，直接 `LIKE` 会受换行、缩进和全角空格影响；中文没有天然词边界，用户输入的是短语片段（"梧桐叶"），不是完整词；A11 要求"命中预先标注的目标集合"，A12 要求"修改正文后再次查询不出现旧文本命中"。数据集规模按 F3 的 1,000 篇估算，单机、离线、无网络。

## 决定

- 迁移 v4 给 `entries` 加一列 `search_text TEXT NOT NULL DEFAULT ''`，内容是**标题与正文的折叠小写副本**：各自把连续空白折叠成一个空格，再整体转小写，标题与正文用换行连接。不建 FTS5 表，不做分词。
- 查询用 `search_text LIKE '%<关键词>%' ESCAPE '\'`。关键词本身也做折叠与小写，并按 `%`、`_`、`\` 转义，因此 `%` 不是通配符，用户输入的标点按字面匹配。
- 写入时机：`save_entry` 每次保存都重算 `search_text`，与 `excerpt` 同一次 UPDATE、同一个事务。删除与恢复不碰它。
- 升级回填：`Library::open` 在迁移前读旧 `user_version`，迁移后若旧版本低于 4，调用一次 `rebuild_search_text` 按现有标题与正文回填全部行。回填只在跨过 v4 的那一次启动执行。
- 标签筛选走 `entry_tags` 的交集：`(SELECT COUNT(DISTINCT et.tag_id) FROM entry_tags et WHERE et.entry_id = entries.id AND et.tag_id IN (...)) = <选中标签数>`。日期范围是 `entry_date BETWEEN` 式的开区间比较（含两端）。三类条件在一条 SQL 里用 `AND` 组合，`LIMIT/OFFSET` 分页。
- 结果排序固定为 `entry_date DESC, created_at_utc DESC, id DESC`，与时间线一致；软删除项在任何条件下都不返回。

## 原因

- 选子串匹配而不是 FTS5：SQLite 的 FTS5 默认分词器对中文按字切分或整段成词，取决于分词器配置，"梧桐叶"这样的短语在默认配置下并不可靠；引入 n-gram 或外部分词器是新的依赖与新的迁移风险，而 1,000 篇量级下 `LIKE` 全表扫描在 debug 构建里首屏也在 100 ms 量级。先把命中正确性做对，再按数据量决定要不要换索引。
- 单独存 `search_text` 而不是每次查询时折叠 `content_text`：折叠与转小写无法走索引，放在 SQL 里会变成每行一次字符串函数调用；存成一列后，`LIKE` 至少在行扫描上是最小成本，且回填只在升级时做一次。
- 大小写折叠只影响匹配、不影响显示：正文保持用户写的原样，搜索 "Travel" 与 "travel" 命中同一批。
- 关键词也折叠空白，是为了让跨行的短语能命中：正文里"梧桐叶被打湿"可能因为换行被拆成两段，折叠成单行后短语才连得上。
- 转义 `%` 与 `_` 而不是当作通配符：用户搜索 "50%" 时想找的是这个字符串，不是"以 50 开头"。这在 A11 里是一条明确的断言。
- 标签用交集而不是并集：多个标签同时选中时，用户的预期是"同时有这些标签"，与多数笔记应用的筛选语义一致；并集会让结果随着勾选变多而膨胀，反而不像"筛选"。
- 回填放在 `Library::open` 而不是迁移 SQL 里：折叠小写是 Rust 函数，SQLite 内置函数做不到一致的 Unicode 处理；放在迁移事务外单独一步，失败时也能看到具体是哪一步出错。

## 备选方案

- **用 FTS5 建虚拟表**：查询更快，但中文分词不可靠，且虚拟表与主表的一致性要自己维护（触发器或应用层同步），迁移与备份都多一层。
- **每次查询时对 `content_text` 现折叠**：不占存储，但每行都要跑一次字符串函数，数据量上去后线性变慢，且没法为将来的排序或高亮复用。
- **只搜 `content_text`，不搜标题**：实现更省事，但用户在标题里写的往往是这篇的主题，漏掉标题会让"找不到"变得难以解释。
- **标签用并集**：勾选越多结果越多，与"缩小范围"的心智模型相反。
- **搜索结果按相关度排序**：需要评分函数与分词，第一版没有可靠的相关度信号；按日期倒序至少和时间线一致，用户能预期新记录在前。

## 影响

- 迁移 v4：`ALTER TABLE entries ADD COLUMN search_text TEXT NOT NULL DEFAULT ''`；`PRAGMA user_version` 变为 4。
- `src-tauri/src/entries/repository.rs` 新增 `search_text`、`collapse`、`escape_like`、`search`、`rebuild_search_text`；`save` 多两个参数（`search_text`、`now_utc` 顺序调整见代码）。
- `src-tauri/src/entries/mod.rs` 新增 `SearchQuery`；`src-tauri/src/tags/repository.rs` 新增 `list_all`。
- 新增两个 Tauri 命令：`search_entries`、`list_tags`（共 17 个）。
- 前端新增 `src/features/search/SearchPage.tsx`，导航"搜索"从占位变为真实页面；搜索结果可进入对应日记并保留"返回搜索"。
- 全表扫描的成本随篇数线性增长；到 M6 的性能基线（A21）时若 1,000 篇以上出现可感知延迟，再评估 FTS5 或 n-gram 索引，届时需要新的 ADR。
- 备份与恢复（M5）不需要额外处理 `search_text`：它是派生列，恢复后可按正文重算；但若恢复流程直接拷贝数据库文件，也要接受列里可能是旧值，恢复后应调用一次回填。
